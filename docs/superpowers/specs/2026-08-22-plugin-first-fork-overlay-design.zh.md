# Plugin-First Fork 覆盖层设计

[English](2026-08-22-plugin-first-fork-overlay-design.md) | 中文

## 目标

fork 将 `master` 保持为可部署的产品分支，同时定期消费 `upstream/master`。只要现有扩展系统能够表达 fork 功能，这些功能就放在独立的插件和组合包中。对 upstream 所有文件的其余修改组成一个规模小、已声明且经过测试的覆盖层，智能体可以在每次 upstream 合并期间调整或退役它，而不会静默保留过时代码。

本项目将现有 fork 迁移到该模型，并替换自动偏向 fork 的冲突解决方式。重新引入 Codex 交互式会话集成是一个独立的后续项目，必须使用本文建立的扩展点。

## 分支和仓库模型

仓库保留标准的 `origin` 和 `upstream` remote。执行 `git fetch upstream` 后，`upstream/master` 是权威的官方来源；本设计不添加 mirror 分支。

`master` 仍是 fork 的工作和发布分支。计划任务或手动触发的同步从当前 fork `master` 创建 `sync/upstream-master`，对 `upstream/master` 执行正常合并，不采用自动的 `ours` 或 `theirs` 冲突偏好，验证生成的 fork 覆盖层，并创建或更新评审 PR。只有经过评审的候选版本才能更新 `master`。

合并历史保持只向前推进。例行同步不会 rebase 或 force-push `master`。一次性迁移可以重写尚未发布的迁移分支，但切换通过经过评审的合并进入 `master`。

## 覆盖层类别

`master` 与合并后的 upstream 树之间的每个差异都属于以下四类之一。

### Fork 自有的包和文件

在记录的 upstream 父提交中，upstream 树不存在 fork 自有路径。典型例子包括新的提供方包、新的 UI 贡献插件、fork 组合包、fork 专用工作流及其测试和文档。Fork 自有的运行时包仍遵循仓库包约定，并使用标准 Cordis 注册生命周期。

如果 upstream 更新在已声明的 fork 自有路径下创建任何路径，就构成所有权冲突。同步会失败，直到智能体选择新位置、采用 upstream 实现或进行明确整合。合并绝不会将 fork 目录自动视为权威来源。

### 组合覆盖层

fork 产品组装位于新的组合包和 profile 覆盖层包中，而不是通过编辑已交付的 upstream 组合包完成。Fork Web 组合包组合 upstream 基础组合包和 Web 组合包，然后按文档化顺序挂载 fork 插件。默认 upstream 组合包在没有 fork 层时仍可使用和测试。

随部署变化的配置值仍属于经过验证的组合包或插件配置。覆盖层不会在 upstream 包中硬编码凭据、模型路由、路径、超时或策略选择。

### 扩展补丁

扩展补丁只修改 upstream 所有文件，用于添加通用注册点，例如 Cordis 服务、事件、slot、注册表或贡献接口。它不包含 fork 功能本身。Fork 自有插件从独立包消费该接口。

没有挂载 fork 插件时，扩展补丁必须保留默认 upstream 行为。其聚焦测试证明空／默认路径和有贡献路径都成立。覆盖层记录会写明所属插件、理由、验证命令以及允许退役该补丁的 upstream 条件。

### 产品补丁

产品补丁是无法通过组合或通用扩展点表达、因而不得不对 upstream 行为进行的修改。这类补丁属于例外，范围狭窄，并且单独评审。禁止替换或冻结现有 upstream 包；产品补丁列出精确文件，并具有明确的文件数和改动行数预算。

每个产品补丁都要说明它保留的可观测行为、失败模式、用于检测行为丢失的测试，以及何时应将补丁 upstream 化或移除。生成产物不是独立的产品补丁：由所属源代码改动和生成器命令一并负责。

## 覆盖层清单

仓库添加 `.fork/overlay.yaml` 作为机器可读的清单。它记录 schema 版本、当前已集成到 `master` 的精确不可变 upstream 提交、fork 自有路径、组合覆盖层、扩展补丁、产品补丁以及 fork 自有工作流路径。每个条目都有稳定 id、精确的路径覆盖范围、所属包或工作流、指向所属 Agent Note 的链接、验证命令和退役条件。相对于记录的 upstream 提交，补丁条目还携带文件数和改动行数预算。

清单描述所有权和验证；Git 仍是代码的真源。仓库不维护内容可能与已应用树发生漂移的重复 `.patch` 文件。

源平面门禁将候选树与清单记录的 upstream 提交进行比较。同步期间，候选版本在源代码合并成功且覆盖层验证开始之前记录传入的 `upstream/master` 提交。门禁强制以下规则：

- 每个仅 fork 存在或已修改的路径都由且仅由一个清单条目覆盖；
- upstream 树中不存在已声明的 fork 自有路径；
- 不得整体替换、删除或声明拥有任何 upstream 所有的包；
- 补丁必须保持在声明的文件和行数预算内；
- 生成输出通过其所属源代码条目获得覆盖；
- 每个验证命令都能解析为仓库脚本或精确的测试目标；
- 差异消失后，陈旧的清单条目会失败，迫使人明确退役它；
- 工作流排除项必须是精确路径，不能写成完整的 `.github/workflows` 目录。

该门禁同时运行于普通 fork 改动和同步 PR。因此，upstream 所有文件的新修改在分类前不能进入 `master`。

## Plugin-First 产品结构

现有 fork 行为按功能逐项迁移。每项功能首先获得行为清单和可运行的验收证据。随后迁移按以下顺序选择：现有 upstream 插件接口；fork 自有插件加组合覆盖层；最小通用扩展补丁加插件；只有前三种方式都无法保留该行为时，才使用产品补丁。

client 从当前完整的 upstream client 开始。Fork UI 行为通过 client 插件、slot、store、渲染贡献和 fork 组合包重新引入。不会将旧 fork client 文件整体复制到 upstream client 上。缺少 UI 插入点时，添加一个带空路径测试的通用扩展补丁，而不是 fork 一份 `InputBar`、conversation shell、theme、runtime 或 package。

Host 能力遵循仓库已经要求的 Service Definition、Service Provider 和 Consumer 包角色。只要外部会话、workspace 置顶、模型路由或超时策略的行为仍然需要，这些功能就保持为独立能力或消费方。过时行为会退役，而不是自动带入新基线。

## Upstream 同步生命周期

同步工作流执行以下生命周期：

1. 获取当前 `upstream/master`，并从 fork `master` 创建或重置候选分支。
2. 在不偏好任何策略的情况下运行 `git merge --no-commit --no-ff upstream/master`。
3. 如果 Git 报告冲突，保留有冲突的候选版本并调用已配置的合并解决智能体。如果没有可用的解析器或解析器失败，则发布诊断信息，并让 PR 保持不可合并。
4. 将 upstream 提交、有冲突的文件、相关覆盖层条目、所属 Agent Note、受影响的包约定和精确验证命令提供给解析器。
5. 要求解析器将每个受影响的覆盖层条目分类为 `preserved`、`adapted`、`upstreamed` 或 `retired`。解析器在选择解决方案前必须理解 upstream 改动，并且不得为 upstream 所有的包选择完整一侧。
6. 仅在源代码冲突解决后重新生成 lockfile 和生成的目录。
7. 运行覆盖层验证、受影响的聚焦测试、源平面类型检查、构建包检查和组装 Web 证明。
8. 让独立评审智能体检查 upstream 改动、覆盖层决策、完整 diff 和验证证据。
9. 更新同步 PR。必需检查通过且评审结论安全时，允许正常合并到 `master`；失败时保持 PR 打开但不部署。

解析器只能写入候选分支。它不能直接 push 到 `master`、修改分支保护、抑制检查或部署。

## 冲突解决智能体约定

合并解决提示词从仓库数据生成，而不是维护成自由格式的工作流 prose。对于每个冲突，它会识别 upstream 意图、面临风险的 fork 行为、清单所有者以及观察该行为的测试。当 upstream 接口演进时，智能体可以同时修改所属插件及其扩展补丁。

智能体报告为每个受影响的覆盖层条目包含一条记录：处置、修改的文件、保留或有意退役的行为、运行的测试以及剩余风险。独立评审人会拒绝没有解释的整文件选择、新的未注册 upstream diff、被削弱的测试、陈旧文档，或仅依据编译结果作出的解决方案。

迁移的实现智能体使用最大推理强度的 `gpt-5.6-luna`。控制器负责规范、实施计划、任务边界、评审、集成检查和最终验收。每个实施任务都有独占的文件所有权，遵循 red-green TDD，并在集成前接受新一轮评审。

## 验证模型

覆盖层门禁证明的是分类，而不是行为。行为验收使用分层证据。

### 源代码和包证据

每个清单条目都列出聚焦测试和受影响包的类型检查。能力改动包含 Service Definition、Provider、Consumer、生命周期和失败路径覆盖。生成的目录以及双语文档使用其所属的仓库门禁。

### 组装 Web 证据

干净 checkout 构建实际的 fork Web 组合。该证明验证输出的应用包含全局 CSS、theme 贡献、client bootstrap 和预期的插件清单。浏览器冒烟测试打开构建后的 fork URL，创建或打开会话，通过常规输入提交提示词，打开设置／菜单控件，并断言浏览器或控制台没有错误。

Web 证明同时针对默认 upstream 组合和 fork 组合运行。这可以防止 fork 插件改变 upstream 默认行为，也能发现通过单元测试但遗漏 CSS 或 client 模块的构建配置。

### 同步模拟

Fixture 覆盖无冲突的 upstream 合并、内容冲突、修改／删除和重命名／删除冲突、upstream 与 fork 自有路径的冲突、过时补丁、补丁预算违规以及损坏的组装 UI 产物。对于每种未解决或未经验证的情况，工作流都快速失败。

## 一次性迁移

迁移从隔离 worktree 中当前 fork `master` 开始，并在修改候选版本前记录恢复 tag。有未提交改动的主 checkout 和无关的未跟踪文件不会被使用或修改。

迁移首先正常合并最新选定的 upstream 基线，然后将完整的 upstream client 确立为 client 基线。在移除前，将当前 fork 行为捕获为功能级验收证据。功能通过 fork 自有插件和组合包逐项恢复；任何必需的 upstream 修改都在同一任务中连同测试加入覆盖层清单。

迁移不保留已回退的 Codex 实现。现有 external-session 包按普通 fork 能力进行评估：可复用的通用部分在针对当前 upstream 架构通过测试后可以保留，而 Codex 专属的进程、MCP、实时流和 UI 工作留在本项目之外。

切换需要完整的覆盖层清单、没有未注册的 upstream diff、没有 fork 自有包替换 upstream 包、相关仓库门禁通过、组装 Web 证据通过，以及针对更新的合成或真实 upstream 提交完成经过评审的 dry-run 同步。

## Codex 后续项目约束

后续 Codex 项目是构建在通用 external-session 接口上的 opt-in 提供方和 Web 组合包。它只能通过已注册的扩展点贡献模式选择、transcript 节点、实时外部输出、审批和 MCP 展示。它不得替换 conversation shell、`InputBar`、theme、client runtime 或默认 Web 组合包。

如果 upstream client 缺少所需的通用扩展点，Codex 项目必须在实现 Codex 插件前，单独添加经过评审且带有默认路径证据的扩展补丁。没有 Codex 组合包时，默认 upstream 组合和 fork 组合保持不变。

## 已否决的替代方案

### 合并时自动偏向 fork

`-X ours` 和按包声明 fork 所有权，可以在没有文本冲突的情况下将新的 upstream 调用方与旧 fork 实现组合起来。编译和单元测试无法证明组装后的 client 包含其样式或兼容的运行时模块。

### 每次同步都 rebase 字面补丁队列

Rebase 后的提交序列使覆盖层显式化，但会重写产品分支，并要求每次 upstream 更新都协调 force-push。清单和正常合并保留相同的所有权信息，而不让重写历史成为例行操作的一部分。

### 将覆盖层保存在另一个仓库

独立的覆盖层仓库可以最大化隔离，但会把本地开发、依赖安装、包链接、发布证据和调试拆分到多个仓库。仓库现有的插件架构已经在一个 workspace 内提供隔离。

### 将完整旧 client 保留为 fork 自有包集合

拥有现有 upstream client 包会阻止 fork 接收 upstream client 架构，并造成广泛的非局部不兼容。迁移保留 upstream 包的 upstream 所有权，并将行为移到贡献中。

## 验收标准

- `master` 从当前 upstream 架构加声明的覆盖层构建 fork 产品。
- 直接消费 `upstream/master`；不需要 mirror 分支。
- `upstream-sync` 不包含自动偏向 fork 一侧的冲突策略，并且不能合并未解决的候选版本。
- fork 与 upstream 合并父提交之间的每个差异都由 `.fork/overlay.yaml` 恰好覆盖一次。
- 没有 fork 自有路径声明拥有或替换 upstream 中存在的包。
- 完整的 upstream client 存在，fork UI 行为由插件、组合包或范围受限的扩展补丁提供。
- 干净的组装 Web 构建会加载 CSS 和预期的插件图，其浏览器冒烟测试会操作会话输入和设置且不产生错误。
- 冲突和所有权冲突模拟会快速失败，并生成可供智能体操作的输入。
- 解析智能体可以仅使用仓库拥有的上下文调整有界补丁，独立评审人可以验证其决策和证据。
- 已回退的 Codex 实现不在迁移结果中；后续可以添加 opt-in Codex 组合包而不改变默认 UI 行为。

## 风险

一次性 client 迁移规模很大，尽管目标覆盖层很小。行为清单和逐功能验收测试降低了 fork 能力被静默丢弃的风险。

某些现有 fork 功能可能暴露 upstream 缺少扩展点的问题。将每项功能作为通用扩展补丁处理，比复制 fork 文件需要更多初始设计工作，但能限制未来的合并成本。

Upstream 可能进行影响许多插件接口的横向改动，而不产生 Git 冲突。覆盖层影响分析、包类型检查、组装产品证据和独立评审可以降低该风险，但没有行为特定测试就无法证明语义兼容性。

智能体解析可能不可用、不正确或范围过大。仅允许写入候选版本的范围、清单预算、必需证据、独立评审和分支保护会将此类失败挡在 `master` 之外。
