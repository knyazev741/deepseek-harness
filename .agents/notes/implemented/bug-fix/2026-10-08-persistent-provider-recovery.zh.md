# Agent Note: 快速重试后的持续提供方恢复

Status: implemented

[English](2026-10-08-persistent-provider-recovery.md) | 中文

## Problem

分支承诺从长期提供方故障中恢复，但空响应、流关闭、过大的 Retry-After 和耗尽的压缩上限可能终止任务。成功的冷却恢复不写入会话日志，客户端因此停留在已耗尽的快速重试计数上。

## Decision

分支覆盖层为每一种规范化提供方失败选择无限冷却恢复。快速重试仍有上限；预算耗尽或无法处理失败时进入冷却。先运行其他请求恢复监听器。随包覆盖层中的每次可取消等待至少为十分钟，并遵循提供方要求的更长延迟。已有重试事件协议记录独立的无限策略链，保持稳定标识和连续尝试计数。

首块与溢出压缩上限委派给重试策略。下游重试后允许新一批有上限的压缩。Gonka 模型策略启用持续摘要恢复；空摘要和快速列表之外的失败也会等待并重试。摘要请求保留自身取消与操作日志，因为它们可以在没有活动回合或步骤时运行。

这部分取代了[冷却恢复](../feature/2026-08-24-fork-llm-rate-limit-cooldown.zh.md)、[首块恢复](../feature/2026-08-27-fork-llm-first-chunk-compaction.zh.md)和[摘要重试](2026-08-29-compaction-summarizer-retry.zh.md)中的停止条件。它们的服务职责、持久进展要求和继续执行理由仍然适用。

## Alternatives considered

增加有限尝试次数只会推迟同一停止点。每次冷却后重启快速批次会增加故障期间的提供方负载。在 agent loop 中重试每个操作还会重复本地修改，并绕过请求与压缩恢复的职责。因此分支扩展现有恢复点。

## Consequences

瞬态失败不再耗尽分支尝试预算。永久提供方错误可能无限等待，直到修正或取消；重试不能保证提供方成功响应。取消与插件释放阻止新尝试。内存等待不是重启调度器；存储、配置、进程崩溃与这些恢复点之外的错误仍是独立失败。

## Testing

真实 agent-loop 场景对十二种错误码分别经历 45 次失败后成功，还覆盖预算耗尽前的 Retry-After 与不支持的错误码。无需密钥的 fork-cooldown 快照在二十次快速重试和两次冷却重试后重新打开生成的日志。压缩测试覆盖新批次、摘要恢复和取消。
