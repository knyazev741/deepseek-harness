# Agent Note: 自动压缩之间必须有 assistant 进展

Status: implemented

[English](2026-09-23-no-consecutive-auto-compaction.md) | 中文

## Problem

首分片超时可能表示提供方过载，而不是上下文过大。重复强制压缩会消耗更多请求来概括已有检查点，却没有推进任务。摘要器重试和冷却等待可能使一次压缩持续数分钟；仅凭开始和结束事件无法知道每次尝试的耗时。

## Decision

基本后端只在从未开始过压缩，或存在更新的已提交 `assistant/message` 时允许自动压缩。现有持久入口状态折叠使该条件跨新轮次、插件继续消息、失败请求和会话恢复仍然有效。失败或取消的压缩也会消耗这次机会。自动区域执行器在追加开始标记之前检查条件，因此直接调用也无法绕过它。

压力压缩执行一次有界处理后返回模型，即使压力仍高于阈值。旧的 `compactionRetries` 配置仍被接受，但不能授权连续自动处理。显式 `/compact` 维护保留其有界多次处理行为，因为用户直接请求了该操作。

[首分片恢复](../feature/2026-08-27-fork-llm-first-chunk-compaction.zh.md) 仍在一次压缩产生持久进展后追加继续消息。后端拒绝再次压缩时，超时会委托给普通重试和冷却。达到首分片插件自身的压缩次数上限也会委托，而不是否决恢复。[半窗口压力策略](2026-09-08-half-window-and-forced-timeout-compaction.zh.md) 保持不变；这些早期决策只被部分替代。

## Alternatives considered

**把压缩重试次数设为一。** 每轮或每进程计数会在继续或重启时重置，而且无法保护其他自动入口。

**任何新消息或轮次都重置限制。** 插件生成的 `continue`、用户重试和失败的 assistant 尝试不代表模型进展，可能重建同一个循环。

**拒绝压缩后停止重试。** 这会失去原有的可用性要求。原始提供方错误必须仍然可以进入普通重试和冷却链。

## Consequences

没有中间的 assistant 响应，自动压缩不能重复改写同一个检查点。仍然过大的请求可能需要显式手动压缩，而不是静默执行多次自动处理。单次压缩内部的提供方重试仍可取消，并在冷却后无限重试；此变更不设置压缩总截止时间。

回归覆盖检查压力和强制溢出、直接区域执行、恢复的会话、失败压缩、继续消息，以及提交响应后重新启用。无头录制会话场景执行一次压缩，随后经历二十次首分片重试、冷却和成功回答，期间没有再次压缩。
