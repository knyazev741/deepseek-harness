# Agent Note: 在半窗口压力下压缩，并在首个分片超时后强制恢复

Status: implemented

[English](2026-09-08-half-window-and-forced-timeout-compaction.md) | 中文

## 问题

默认的 `0.8` 压力阈值会让 400k 上下文的对话增长到 320k token 后才开始压缩。DeepSeek 的回答质量和首个分片延迟会在此之前恶化，而且等请求已经如此庞大时才启动摘要器，会降低恢复可靠性。另一项改动还把 `FIRST_CHUNK_TIMEOUT` 交给正常压力检查，因此低于阈值的超时会重试未改变的请求，而不会复现已经验证的先压缩再继续流程。

## 决策

`compaction-basic` 将 `thresholdRatio` 的默认值设为 `0.5`，因此对于 400k 上下文的模型，除非配置提供其他比例，否则会在 200k token 时开始自动步骤边界压缩。精确的提供方／模型策略仍可覆盖服务默认值。

选择性启用的 `fork-llm-first-chunk-timeout` 恢复独立于普通压力。每个 `FIRST_CHUNK_TIMEOUT` 都会请求选定的压缩服务执行强制 `context-overflow` 压缩。持久替换会结束失败轮次，并在 agent 到达 `idle` 后排入由插件生成的 `continue` 消息，具体由[首个分片恢复决策](../feature/2026-08-27-fork-llm-first-chunk-compaction.zh.md)定义。没有持久替换时，会委托给下游 retry 和 cooldown 策略。

## 备选方案

**保留 `0.8` 默认值，仅配置已知的 400k 模型。** 否决，因为最后四分之一的质量退化是通用运行属性，而遗漏模型覆盖会静默恢复过晚阈值。需要更晚阈值的部署仍可显式覆盖。

**仅为首个分片超时使用独立的 `0.5` 阈值。** 否决，因为它无法防止成功请求在没有错误时累积退化上下文，而且超时也可能在半窗口压力之前需要恢复。

**使用普通压力限制首个分片恢复。** 否决，因为超时本身就是恢复信号。观察到的会话中，即使重复请求没有进展，该方案仍会阻止压缩和新轮次 `continue` 路径。提供方过载也可能导致超时，但没有持久压缩进展时会回退到现有 retry 和 cooldown 链。

## 后果

长会话会更早压缩，因此会更频繁地承担摘要和 KV cache 替换成本，以换取普通请求远离模型窗口中质量退化的尾部。首个分片超时即使在低上下文压力下也可能在提供方故障期间启动摘要器；取消、摘要器重试策略、压缩重试上限和持久进展检查会限制该恢复。单元覆盖固定半窗口默认值和强制触发器，真实 driver 覆盖固定从错误到 `idle` 的 `continue` 转换。
